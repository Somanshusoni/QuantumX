Project Overview

This project is a simulation of a financial exchange. It was built to demonstrate how to handle concurrent requests, manage state between a persistent database and an in-memory cache, and process real-time data using WebSockets.

The system is broken down into three main components:

  • The REST API: Handles user registration, KYC data, and order placement.
  • The Matching Engine: A continuous background loop that reads the order book and matches buyers with sellers.
  • The Bot Swarm: A separate script that generates automated trading volume to simulate an active market.

Core Libraries & Technologies

1. FastAPI

Use Case: Building the main web server and REST API endpoints.

Why it was chosen: FastAPI is built on ASGI (Asynchronous Server Gateway Interface). This allows the server to handle multiple web requests (like order placements) simultaneously without blocking. It also provides built-in support for WebSockets, which is used here to push live trade notifications to the frontend without requiring the user to refresh the page.

2. Redis (redis-py)

Use Case: The In-Memory Order Book and Message Broker.

Why it was chosen: Traditional SQL databases are too slow for order matching. This project uses Redis ZSETs (Sorted Sets). When a user places an order, it is added to a Redis ZSET. Redis automatically sorts these orders by price, allowing the Python matching engine to instantly grab the highest bidder and lowest seller in O(log(N)) time. Redis Pub/Sub is also used to pass messages from the background engine to the FastAPI WebSockets.

3. SQLAlchemy & PostgreSQL / SQLite

Use Case: Persistent Data Storage.

Why it was chosen: SQLAlchemy acts as the ORM (Object-Relational Mapper). While Redis handles the temporary, fast-moving order book, SQLAlchemy manages the permanent records: user credentials, KYC details (Aadhaar/Phone), total fiat balances, and stock holdings. It ensures data integrity so that if the server crashes, users do not lose their portfolios.

4. Asyncio & Httpx

Use Case: The Automated Trading Swarm.

Why it was chosen: To simulate a real market, multiple bots need to place orders at the same time. asyncio allows a single Python script to run 10+ bot loops concurrently. httpx is the asynchronous HTTP client the bots use to send network requests to the FastAPI server, behaving exactly like a real user clicking buttons on the frontend.

5. Math & Random

Use Case: Price Oscillation Logic.

Why it was chosen: The bot script uses Python's built-in math.sin() function combined with time.time() to create a sine wave. This mathematical baseline forces the simulated stock prices to naturally drift up and down over time, rather than moving completely randomly, while random.uniform() adds micro-volatility to each tick.

System Rules

  • Financial Safety: When an order is placed, the required fiat or shares are temporarily moved to a locked state in the database to prevent double-spending.
  • Market Orders: Implements "Fill-And-Kill" logic. If a market order exhausts available liquidity, the remainder is immediately canceled to prevent infinite slippage.
  • Admin Isolation: Administrative functions (modifying balances) are decoupled from the public API and run on a separate local port, requiring a database-verified JWT flag.
