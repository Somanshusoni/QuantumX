ABSTRACT



In the modern financial ecosystem, real-time trading platforms demand systems with extraordinarily low latency, extremely high concurrency, and impenetrable transactional integrity. The project, titled "Quantum Exchange," seeks to design, implement, and evaluate a comprehensive stock market simulation environment. This platform mirrors the rigorous architectures utilized by global financial institutions to handle thousands of concurrent trades, process real-time market data, and execute complex algorithmic matchmaking without falling victim to common data race conditions.

The developed system features a decoupled microservices architecture. It utilizes a FastAPI-based gateway for user authentication, order ingestion, and API handling. Concurrently, a robust, standalone Python background worker functions as the execution engine, leveraging Redis Sorted Sets (ZSET) to orchestrate a First-In-First-Out (FIFO) limit order book. The platform maintains ACID compliance for user portfolios via an SQLite backend managed by SQLAlchemy, ensuring fiat balances and stock holdings are accurately tracked through locking mechanisms.

Furthermore, the project includes the implementation of automated Market Maker bots designed to simulate real-world liquidity and price volatility. Through the extensive use of WebSockets, the platform successfully pushes live price updates to a reactive, Python-driven NiceGUI frontend, providing end-users with real-time candlestick visualizations powered by Apache ECharts. This report details the theoretical foundation, system design, core implementation, and error-handling strategies utilized to prevent slippage and ghost share allocation.

CHAPTER 1: INTRODUCTION

1.1 Overview

The evolution of financial technology has shifted global stock exchanges from crowded trading floors into purely digital, high-frequency execution environments. Modern stock exchanges, such as the New York Stock Exchange (NYSE) or the National Stock Exchange of India (NSE), handle millions of transactions per second. At the heart of these massive systems lies the Limit Order Book (LOB) and the Order Matching Engine, which pair buyers and sellers fairly based on price and time priority.

The "Quantum Exchange" is a highly ambitious software engineering project aimed at recreating the core technical infrastructure of a modern financial exchange. Rather than relying on simple database queries which are prone to bottlenecks, Quantum Exchange implements an in-memory execution strategy using Redis. This allows orders to be queued, scored, and matched in sub-millisecond intervals.

Furthermore, an exchange is only as useful as its ability to communicate with its users. Therefore, the project implements a fully asynchronous Python backend capable of streaming live price data to users' browsers via WebSockets, ensuring that the UI reflects the true state of the market instantly.

1.2 Motivation

The primary motivation for developing Quantum Exchange stems from the sheer architectural complexity of financial systems. Traditional web applications typically follow a standard Request-Response cycle: a user submits a form, the database updates, and an HTML page is returned. However, in trading systems, this paradigm fails completely.

If two users attempt to buy the exact same share of stock at the exact same millisecond, a standard database architecture will suffer from a "Race Condition," resulting in both users being charged, but only one receiving the stock, or the system crashing. Financial engineering requires the implementation of queues, locks, and strict atomic operations.

Building this project provides profound insight into Distributed Systems, Publisher/Subscriber communication models, and asynchronous programming in Python. By tackling problems like double-spending, ghost shares, and slippage, the developer gains critical experience in building mission-critical enterprise software.

Moreover, the integration of Automated Market Makers (bots) introduces elements of algorithmic trading and chaos engineering. Testing how a platform behaves when flooded with millions of automated, randomized requests ensures that the underlying architecture is bulletproof.

1.3 Problem Statement

The core problem addressed by this project is the lack of open-source, easily understandable, and full-stack trading engines built natively in Python. Existing trading simulation platforms often abstract away the complexity of the order book, relying on external APIs for pricing data, or they utilize monolithic database structures that cannot scale under high frequency trading (HFT) loads.

Specifically, the project seeks to solve the following technical challenges:

  • Order Concurrency: Preventing data corruption when thousands of market orders hit the server concurrently.
  • Real-Time Data Delivery: Traditional HTTP polling is too slow and resource-intensive for live tickers. A low-latency push mechanism must be established.
  • Fair Matching: Ensuring that orders are matched strictly based on Price-Time Priority (FIFO) without bias.
  • Financial Security: Preventing users from spending fiat currency they do not have, or selling shares they do not own, even when circumventing frontend UI limits.

CHAPTER 2: LITERATURE REVIEW & THEORETICAL BACKGROUND

2.1 The Mechanics of Financial Exchanges

A financial exchange acts as a central marketplace where financial instruments such as equities, commodities, and derivatives are traded. Historically, exchanges operated via open outcry systems on physical trading floors. Brokers would shout bids and offers, and matches were made manually. Today, exchanges are essentially massive data centers running proprietary matching engines.

The primary function of an exchange is to provide liquidity and price discovery. Price discovery is the mechanism through which the interactions of buyers and sellers determine the current fair market value of an asset. This is achieved through the continuous aggregation of Limit Orders.

2.2 The Limit Order Book (LOB)

The Limit Order Book is the central data structure of any exchange. It is an electronic record of all outstanding buy and sell orders for a specific asset, organized by price level.

The LOB consists of two sides:

  • The Bid Side (Buyers): Contains orders from users wishing to purchase the asset. Bids are sorted in descending order, meaning the highest price a buyer is willing to pay sits at the top of the book.
  • The Ask Side (Sellers): Contains orders from users wishing to sell the asset. Asks are sorted in ascending order, meaning the lowest price a seller is willing to accept sits at the top of the book.

The difference between the highest bid and the lowest ask is known as the "Spread." When a user submits a Market Order (an order to buy or sell immediately at the best available price), the engine traverses the order book, absorbing liquidity from the top down until the order quantity is fulfilled.

2.3 Order Matching Algorithms (FIFO)

To ensure fairness, exchanges must implement strict algorithms determining which orders get executed first when multiple orders exist at the same price point. The most universally accepted standard is the Price/Time Priority algorithm, commonly referred to as FIFO (First-In, First-Out).

Under FIFO rules, priority is determined first by price. A buyer offering ₹105 will always jump ahead of a buyer offering ₹100. However, if two buyers both offer ₹105, priority is determined by time. The buyer who submitted their order first, down to the nanosecond, will be placed higher in the queue and matched first.

In the Quantum Exchange, implementing strict FIFO in Python natively is difficult because Python lists are computationally expensive to re-sort continuously. The architecture follows a microservices-inspired design, decoupling the user-facing APIs from the order execution engine. When an order is placed, it is pushed to a Redis queue rather than executed synchronously. A continuous background worker (the Order Engine) consumes this queue, utilizes Redis Sorted Sets (ZSET) to maintain time-price priority, matches buyers and sellers, calculates maker/taker fees, updates user portfolios in the PostgreSQL database, and triggers WebSocket notifications. A ZSET automatically sorts its elements based on a numerical "Score."

By mathematically combining the Order Price and the Unix Timestamp into a single integer score, Quantum Exchange leverages the C-compiled speed of Redis to sort the entire order book in logarithmic time `O(log(N))` upon every single insertion.

2.4 WebSockets vs HTTP Polling

Traditional web applications rely on the HTTP protocol, which operates on a Request-Response paradigm. The client asks the server for data, the server responds, and the connection is closed. If a user wants to see the latest stock price, their browser would have to constantly refresh or send HTTP requests every second (known as Long Polling).

Polling is wildly inefficient for financial applications. If 10,000 users are polling the server every second, the server must process 10,000 HTTP headers, authenticate 10,000 tokens, and open/close 10,000 TCP connections per second. This inevitably leads to server crashes and massive latency.

Quantum Exchange utilizes the WebSocket Protocol (ws:// or wss://). WebSockets establish a single, persistent, bi-directional TCP connection between the client and the server. Once the "handshake" is complete, the connection remains open permanently.

This allows the FastAPI backend to "Push" data down the pipe to the client the exact millisecond a trade executes, without the client ever needing to ask for it. This drops data latency from hundreds of milliseconds down to virtually zero, enabling the real-time flickering numbers seen on professional trading terminals.

CHAPTER 3: TECHNOLOGY STACK SELECTION

3.1 Python as the Core Language

Python was chosen as the foundational programming language for the Quantum Exchange due to its exceptional readability, massive ecosystem of financial libraries, and natively supported asynchronous capabilities (asyncio). While languages like C++ or Rust are traditionally used for ultra-high-frequency trading systems due to their raw execution speed, Python excels in architectural modeling, rapid prototyping, and web framework integration.

By delegating the computationally heavy sorting logic to Redis (which is written in C) and database interactions to SQLAlchemy, the Python layer acts purely as an asynchronous orchestrator, effectively eliminating the typical speed bottlenecks associated with Python's Global Interpreter Lock (GIL).

3.2 FastAPI: The API Gateway

FastAPI is a modern, fast (high-performance) web framework for building APIs with Python 3.7+ based on standard Python type hints. It was selected over traditional frameworks like Django or Flask for several critical reasons:

  • Asynchronous Native: FastAPI is built on Starlette, meaning it inherently supports `async def` routing. This allows the server to handle tens of thousands of concurrent WebSocket connections without blocking the main execution thread.
  • Automatic Validation: By utilizing Pydantic models, FastAPI automatically validates incoming JSON payloads. If a user tries to submit a text string instead of a numerical price, FastAPI rejects the request with a 422 Unprocessable Entity error before it ever reaches the application logic.
  • Auto-Generated Documentation: FastAPI automatically generates interactive Swagger UI documentation, drastically accelerating the testing and debugging phases of development.

3.3 NiceGUI: State-Driven Frontend

Building a complex, real-time UI traditionally requires a completely separate JavaScript codebase (e.g., React, Vue, or Angular) communicating with the Python backend via REST APIs. This drastically increases project complexity, deployment difficulty, and the likelihood of cross-origin (CORS) errors.

Quantum Exchange utilizes NiceGUI, an incredibly powerful Python UI framework based on Vue.js and Tailwind CSS. NiceGUI allows the developer to construct complete HTML interfaces, handle button clicks, and manage dynamic states entirely within Python code.

When a variable in the Python state dictionary is updated (e.g., `state["live_price"] = 150`), NiceGUI automatically communicates with the browser via an underlying WebSocket and redraws only that specific HTML element on the user's screen. This enables real-time reactivity without writing a single line of JavaScript.

3.4 Redis: In-Memory Data Structure Store

Redis is the absolute backbone of the Quantum Exchange. It is an open-source, in-memory data structure store, used as a database, cache, and message broker. Because it stores data in RAM rather than on a spinning hard drive or SSD, its read/write speeds are measured in fractions of a millisecond.

Redis is used for three critical functions in this project:

  • Order Queue (`r.rpush`): When users submit orders, they are pushed into a Redis List. The engine pops them off one by one, ensuring a single-threaded, race-condition-free ingestion pipeline.
  • The Order Book (`r.zadd`): Redis Sorted Sets automatically sort bids and asks based on custom scoring algorithms, acting as the limit order book.
  • Pub/Sub (`r.publish`): The Publish/Subscribe paradigm allows the matching engine to announce a trade to the Redis network. The FastAPI WebSocket manager subscribes to this channel and immediately forwards the data to connected users.

3.5 PostgreSQL & SQLAlchemy

While Redis handles ephemeral, fast-moving data (like the active order book), a persistent relational database is strictly required for long-term data storage. PostgreSQL was chosen for its robust ACID compliance and scalability, making it suitable for production-grade financial records.

SQLAlchemy serves as the Object Relational Mapper (ORM). It allows the developer to interact with the database using Python classes rather than raw SQL strings. This significantly reduces the risk of SQL Injection attacks and allows for complex relationships between tables (e.g., A User has many Holdings, a Trade involves a Buyer and a Seller).

Database Schema (Core Entities)

The database consists of several interconnected tables:

  • Users Table: Stores email, hashed passwords (bcrypt), KYC details, and active fiat balances.
  • Holdings Table: Tracks which user owns how many shares of a specific stock, including the average buy price and the number of shares currently "locked" in pending sell orders.
  • Trades Table: A permanent, immutable ledger of every successfully matched transaction, acting as the ultimate source of truth for the exchange's history.
  • Companies Table: Stores static metadata regarding listed equities, such as the stock symbol, company name, market cap, and total issued shares.

CHAPTER 4: SYSTEM ARCHITECTURE & DESIGN

4.1 Decoupled Microservice Architecture

One of the most critical design decisions in Quantum Exchange was the complete separation of the API Gateway (`main.py`) from the Trading Engine (`engine.py`). In a poorly designed monolithic application, the web server processes the HTTP request, locks the database, attempts to match the order, updates the database, and then returns the HTTP response.

This monolithic approach is disastrous under heavy load. If an order takes 50 milliseconds to match, the web server is blocked. If 1,000 users submit orders simultaneously, the server queue backs up, HTTP requests timeout, and the entire platform crashes.

Quantum Exchange implements an asynchronous message queue architecture:

  1. The User submits an order to FastAPI.
  2. FastAPI performs basic validation (e.g., Does the user have enough money?). If yes, it deducts the money locally and pushes an "Order Ticket" string into a Redis Queue.
  3. FastAPI immediately responds to the user with a "200 OK: Order Submitted" message. The HTTP connection is closed instantly, freeing the web server to handle the next user.
  4. Completely independent of the web server, the Python daemon `engine.py` is running in an infinite loop. It pops the order from Redis, processes the complex matchmaking logic in the background, and saves the final result to the database.

This architecture allows the system to absorb massive spikes in user traffic (Order Bursting) because inserting a string into Redis takes virtually zero time. The engine can chew through the backlog at its own pace without ever crashing the frontend web server.

4.2 The Publisher/Subscriber (Pub/Sub) Notification Tunnel

Because the web server and the trading engine are completely disconnected, a communication mechanism is required to notify the web server when a background task (an order match) is completed.

This is achieved using the Redis Pub/Sub protocol. The matching engine acts as the Publisher. Upon successfully executing a trade, it broadcasts a JSON payload containing the updated stock price and the specific IDs of the buyer and seller to a specific Redis channel.

The FastAPI instance acts as the Subscriber. It continuously listens to this channel. When it intercepts a message, it routes that message directly into the active WebSocket connections of the specific users involved, triggering a UI update on their screen.

CHAPTER 5: IMPLEMENTATION DETAILS & CODE ANALYSIS

5.1 Authentication & Security (main.py)

Security is paramount in financial software. The system implements JWT (JSON Web Tokens) to maintain stateless authentication. When a user logs in, their password is hashed using `bcrypt` and compared against the database. If successful, FastAPI generates an encoded token containing the User's ID and an expiration timestamp.

# Token Generation Logic def create_access_token(data: dict, expires_delta: timedelta | None = None): to_encode = data.copy() expire = datetime.utcnow() + (expires_delta or timedelta(minutes=15)) to_encode.update({"exp": expire}) encoded_jwt = jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM) return encoded_jwt

For every subsequent request to buy or sell a stock, the frontend must attach this token in the Authorization Header. A Dependency Injection function (`get_current_user`) intercepts every request, decodes the token, and fetches the user object from the database, effectively preventing unauthorized actions.

5.2 The Heart of the Machine: engine.py

The Order Matching Engine contains the most complex logic in the entire system. It must continuously loop, parse JSON tickets, apply mathematical scoring, manipulate Redis structures, calculate taxation, and orchestrate atomic database commits.

Time-Priority Scoring Algorithm

To enforce FIFO (First-In, First-Out) matching within the Redis Sorted Set, the engine utilizes a massive integer multiplier. For a BUY order, higher prices must rank first, and older timestamps must rank first. Therefore, the score is calculated as `(Price * 1,000,000,000) - Timestamp`.

# Time-Priority Scoring Logic TIMESTAMP_MULTIPLIER = 1_000_000_000 if ticket["side"] == "BUY": score = (ticket["price"] * TIMESTAMP_MULTIPLIER) - ticket["timestamp"] else: # Sell orders want LOWER prices, so we ADD the timestamp score = (ticket["price"] * TIMESTAMP_MULTIPLIER) + ticket["timestamp"] key = f"bids:{symbol}" if ticket["side"] == "BUY" else f"asks:{symbol}" r.zadd(key, {order_json: score})

Once inserted, the engine aggressively loops, attempting to match the highest ranking Bid against the lowest ranking Ask until the liquidity spread is resolved.

5.3 Taxation and Settlement

When a match occurs, the engine initiates the settlement process. In a real exchange, liquidity providers (Makers) are incentivized, while liquidity takers (Takers) are charged higher fees. The engine identifies who was sitting in the book first by comparing their order timestamps.

# Maker/Taker Fee Calculation if top_buyer["timestamp"] < top_seller["timestamp"]: buyer_fee_rate = 0.000 # Buyer was sitting in book (MAKER) seller_fee_rate = 0.002 # Seller aggressively hit the book (TAKER) else: buyer_fee_rate = 0.002 # Buyer aggressively hit the book (TAKER) seller_fee_rate = 0.000 # Seller was sitting in book (MAKER)

The `execute_trade_in_db` function then performs the atomic database transaction. It deducts the exact fee amount from the user's fiat balance, transfers the underlying asset shares from the seller's holdings to the buyer's holdings, and routes the collected taxes directly to the Admin's treasury account (User ID 1).

5.4 Automated Market Makers (bot.py)

A stock exchange without liquidity is functionally useless. To simulate an active, buzzing market environment, the project implements a "Chaos Bot" architecture. These autonomous scripts authenticate themselves via the API and rapidly spam the exchange with opposing buy and sell limit orders.

# Chaos Liquidity Injection def run_chaos_loop(token_buy, token_sell, assets): while True: symbol = random.choice(list(assets.keys())) current_fair_value = assets[symbol] + random.uniform(-5.0, 5.0) bid_price = round(current_fair_value - random.uniform(0.5, 2.0), 2) ask_price = round(current_fair_value + random.uniform(0.5, 2.0), 2) place_order(token_buy, symbol, "BUY", bid_price, qty) place_order(token_sell, symbol, "SELL", ask_price, qty) time.sleep(0.5)

By injecting thousands of these micro-orders per minute, the bots create a tight bid-ask spread and generate massive amounts of price action data, which is then plotted beautifully on the frontend charts.

CHAPTER 7: CRITICAL ERROR HANDLING

7.1 Mitigating "Ghost Shares"

One of the most dangerous edge cases in a decoupled architecture is system desynchronization. When a user submits a sell order, FastAPI immediately "locks" those shares in the PostgreSQL database so the user cannot sell them twice. The order sits in the Redis queue.

If the engine crashes while orders are sitting in the Redis Order Book, the user's shares remain "locked" in the PostgreSQL database permanently. To fix this, an End-of-Day settlement script is executed upon a shutdown signal (CTRL+C).

To solve this, the engine intercepts the `KeyboardInterrupt` signal and executes a graceful `end_of_day_settlement()` function. This function iterates through the entire database, sets all `locked_qty` back to 0, and refunds all `locked_fiat` back to available balances before safely shutting down.

7.2 Slippage Tripwires & Circuit Breakers

In automated markets, a lack of liquidity combined with a large "Market Order" can cause catastrophic "Slippage," where a user intending to buy a stock at ₹100 ends up paying ₹500 because the engine ate through the entire order book. The project implements a hardcoded universal slippage circuit breaker.

# Slippage Tripwire Logic current_ltp_raw = r.get(f"LTP:{symbol}") if current_ltp_raw: current_ltp = float(current_ltp_raw) if current_ltp > 0 and (matched_price > current_ltp * 1.20 or matched_price < current_ltp * 0.80): print(f"🛑 SLIPPAGE TRIPWIRE! Blocked rogue execution.") break

If an algorithmic match attempts to execute at a price greater than a 20% deviation from the Last Traded Price (LTP), the engine instantly aborts the execution, deletes the offending order from the book, and protects the ecosystem from a flash crash.
